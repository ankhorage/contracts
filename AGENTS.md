# AGENTS.md

## Scope

This file applies to the whole `ankhorage/contracts` repository.

`@ankhorage/contracts` owns the canonical, serializable, provider-neutral contracts shared across Ankhorage packages. It defines persisted shapes, public domain DTOs, focused structural validators/parsers, IDs/refs, and intentionally exported constants/types. It does **not** own Runtime execution, Studio authoring UX, provider adapters, infrastructure generation, deployment execution, or persistence implementation.

## Architectural north star: one canonical contract per concept

Every persisted or cross-package concept must have one clear canonical owner and one canonical serializable representation.

Before implementing anything, ask:

> Is this a portable domain shape that multiple Ankhorage packages must agree on, or is it execution/authoring/provider behavior that belongs to another package?

If it is a portable serializable shape, Contracts may own it. If it describes how the shape is executed, generated, rendered, deployed, edited, persisted, or provided, keep that behavior in the owning package and expose only the minimum provider-neutral reference/configuration required by the contract.

Required direction:

- `ankh.config.json` / `AppManifest` is the canonical persisted application manifest truth.
- Contracts defines **shape and structural validity**; semantic readiness and execution belong to owner packages.
- One concept must not be persisted in two parallel locations.
- A provider-neutral concept must not expose a concrete provider SDK/API response shape.
- Runtime, Studio, Infra, Deploy, adapters, templates, and generated apps consume released Contracts APIs; they must not copy contract types locally.
- Public contract changes must update TypeScript types and runtime structural parsing together.
- Focused subpath contracts should remain importable without pulling unrelated domain implementation into consumers.

Conceptual ownership:

```text
@ankhorage/contracts
  canonical serializable shapes
  structural parsing/validation
  stable IDs/refs/DTOs
  provider-neutral authored configuration
          |
          +--> Runtime      execution
          +--> Studio       authoring UX
          +--> Infra        infrastructure generation
          +--> Deploy       deployment semantics
          +--> Templates    authored starter manifests
          +--> Adapters     provider implementation
```

## Core architectural rules

### Canonical state only

Do not add duplicate persisted sources of truth, dual-write fields, aliases, shadow registries, temporary mirror properties, or package-local copies of an existing canonical concept.

When a contract is replaced, update first-party consumers in the coordinated roadmap/release sequence and remove the obsolete contract instead of preserving two writable models.

### No legacy or compatibility architecture

Do not add or keep legacy, deprecated, compatibility, fallback, shim, bridge, migration-wrapper, or dual old/new code paths unless an explicitly approved roadmap says Contracts itself owns a versioned migration mechanism.

In particular, do not make structural parsers silently transform removed first-party shapes into new ones just to keep old consumers compiling.

### Contracts owns shape, not behavior

Allowed:

- serializable domain interfaces/types;
- stable IDs and references;
- provider-neutral configuration;
- DTOs/event/value shapes;
- structural runtime validators/parsers;
- constants that define canonical finite value sets;
- focused resolver helpers only when normalization/defaulting is itself part of the canonical contract.

Not allowed:

- HTTP requests;
- filesystem/process access;
- React/React Native UI;
- Expo behavior;
- Studio state/UI logic;
- Supabase/Auth0/Cognito/etc. execution;
- database queries;
- infrastructure generation;
- app deployment execution;
- provider SDK response objects;
- generated server/runtime implementation.

If a consumer needs executable behavior, implement that behavior in its owning package and keep Contracts limited to the portable shape/reference needed to invoke it.

### Provider-neutral public model

Do not leak provider-specific implementation details into portable contracts merely because the current implementation uses one provider.

Avoid canonical fields shaped around:

- Supabase REST/PostgREST internals;
- Fastify route/runtime objects;
- Expo implementation details;
- EAS/Apple/Google SDK response structures;
- provider CLI flags;
- raw provider configuration escape hatches such as `Record<string, unknown>` when a real portable concept can be modeled explicitly.

Opaque provider IDs/references are acceptable where the provider choice itself is authored state. Provider behavior remains package-owned.

### Structural validation and semantic validation are different

Contracts owns structural validity:

```text
Is this value shaped like the canonical contract?
```

Owner packages own semantic readiness/capability checks:

```text
Can this configuration actually run/deploy/connect with the selected provider/environment?
```

Do not make Contracts depend on network state, installed tools, credentials, provider availability, filesystem state, or runtime capabilities.

### Type and parser changes move together

If a persisted `AppManifest` shape changes:

1. update the canonical TypeScript contract;
2. update the corresponding structural parser/validator in the same change;
3. update top-level allowed-key policy where applicable;
4. update focused parser tests;
5. update public exports/subpaths if the contract is public;
6. remove obsolete parser acceptance for removed first-party properties;
7. add a changeset.

A field that exists only in TypeScript or only in the parser is an invalid Contracts state.

## AppManifest ownership

`AppManifest` is the canonical serializable app/project manifest shape.

Rules:

- do not add a second manifest model for a package-specific workflow;
- package-specific semantics should consume canonical manifest sections rather than copying them;
- top-level additions must be intentional domain concepts, not convenience storage for one consumer;
- unknown/removed canonical fields should not silently become accepted extension channels;
- secrets must never be embedded into ordinary manifest contracts; use explicit secret references/contracts where appropriate.

When deciding whether data belongs in `AppManifest`, prefer desired/authored state. Runtime observations, provider responses, execution history, caches, ledgers, and generated artifacts belong elsewhere.

## Public API rules

Public exports are explicit.

When adding or changing a public contract/helper:

1. place it in the focused owning source module;
2. export it from the intended public entrypoint;
3. add/update a package subpath when a focused consumer boundary materially benefits from it;
4. add tests that exercise the public symbol/shape so Knip recognizes the intended surface;
5. update runtime parser coverage where persisted data is involved;
6. add a changeset for published API changes.

Do not rely on deep imports from consumers. If consumers need a symbol, export it intentionally.

Prefer focused modules and intentional exports over growing unrelated omnibus files.

## Source organization and size

Keep source boundaries focused by domain.

Common locations:

```text
src/types.ts                  shared/top-level manifest types
src/appManifest.ts            canonical top-level parser
src/appManifest/*             focused manifest subtree validators
src/data/*                    API/data operation/schema/ref contracts
src/auth.ts                   auth contracts
src/db.ts                     database contracts
src/deploy.ts                 app deployment contracts
src/media.ts                  media contracts
src/secrets.ts                secret-reference/store contracts
src/storage.ts                storage contracts
src/ui.ts                     UI DTO/contracts
src/*.test.ts                 Bun tests
.changeset/                   release notes
paradox/                      generated docs output
```

The repository follows the Ankhorage soft 50-line rule for functions/files where practical. Prefer extracting one focused concept/helper per file rather than letting contract and validator modules become catch-all implementations.

Do not weaken architecture merely to satisfy the size rule; split by real domain responsibility.

## Strict TypeScript and validation rules

Do not use:

- `any`;
- `@ts-ignore`;
- `@ts-expect-error` as an implementation workaround;
- ESLint disable comments to bypass architecture/type errors;
- weakened compiler/lint settings;
- unchecked provider payload casts as canonical contracts.

For parser code, narrow `unknown` deliberately with focused structural predicates. Keep validators deterministic, side-effect free, and offline.

## Tests and validation

Tests should be behavior-focused and prove both valid and invalid canonical shapes.

For persisted/public contract changes, cover at minimum:

- valid canonical shape accepted;
- malformed shape rejected;
- removed/forbidden parallel shape rejected where relevant;
- unrelated existing manifest sections remain valid;
- public exports/subpaths remain intentional;
- no provider/runtime package dependency is introduced accidentally.

Preferred full validation before handoff:

```bash
bun run build
bun run lint:fix
bun run format
bun run format:check
bun run knip
bun run test
bun run typecheck
bun run docs
bun run changeset:status
```

Available package scripts include:

```bash
bun run build
bun run changeset
bun run changeset:status
bun run docs
bun run knip
bun run lint
bun run lint:fix
bun run format
bun run format:check
bun run test
bun run typecheck
bun run version-packages
```

Notes:

- `bun run test` runs Bun tests under `src/`.
- `bun run typecheck` runs TypeScript with `--noEmit`.
- `bun run build` emits `dist/`.
- `bun run docs` regenerates Paradox output.
- `README.md` is generated by Paradox; do not edit it manually.

## Changesets and release boundaries

Add a changeset for any published contract change, including:

- new/removed/changed public types;
- changed persisted manifest shapes;
- parser acceptance/rejection changes;
- package export/subpath changes;
- changed public constants or DTO semantics.

Choose patch/minor/major according to the package's current release policy and the actual consumer impact; do not understate a breaking public removal merely to avoid downstream work.

Cross-repository work must respect release boundaries:

```text
Contracts change
  -> PR
  -> merge
  -> release
  -> downstream package updates dependency
```

Do not bridge an unreleased Contracts change with deep imports, Git SHA dependencies, copied types, `file:` dependencies, or duplicated local interfaces.

## Dependency rules

Contracts should remain near the bottom of the dependency graph.

Current runtime dependency is intentionally small (`@ankhorage/color-theory`). Do not add dependencies on higher-level Ankhorage packages such as Studio, Runtime, Infra, Deploy, Templates, provider adapters, or application hosts.

For any new dependency:

- justify why a canonical contract cannot be expressed locally with TypeScript primitives/provider-neutral types;
- avoid pulling execution/provider/runtime dependencies into Contracts;
- preserve focused subpath usability and side-effect-free imports.

## Working style for agents

Before coding:

1. read the active roadmap/issue first;
2. inspect current public types and package exports;
3. inspect the matching runtime structural parser;
4. inspect behavior-focused tests for the domain;
5. identify every duplicate/obsolete canonical shape the change intends to replace;
6. identify the release boundary and changeset impact.

While coding:

1. keep one canonical contract;
2. change type + parser + tests together;
3. keep structural validation side-effect free;
4. keep execution/provider semantics out of Contracts;
5. remove obsolete first-party shapes instead of adding aliases;
6. keep modules focused and strict;
7. update public exports intentionally;
8. do not edit generated README output manually.

Before final handoff:

1. run full validation or clearly report what was not run;
2. include issue/PR/commit references;
3. list public API/persisted-shape changes;
4. list removed obsolete contracts;
5. mention changeset path and intended release impact;
6. identify the exact downstream release gate/follow-up issue.

## Common pitfalls

- Updating a TypeScript interface without updating its runtime parser.
- Accepting a new parser field without adding it to the public contract.
- Keeping old and new persisted fields writable at the same time.
- Adding `legacy*`, `deprecated*`, compatibility aliases, or silent parser transforms.
- Modeling provider implementation details as portable domain state.
- Putting Runtime/Infra/Studio behavior into Contracts because it is convenient for one consumer.
- Using a generic `Record<string, unknown>` escape hatch instead of a real canonical concept.
- Adding public exports without tests, causing Knip/public-surface drift.
- Forgetting a changeset for a public contract/parser change.
- Editing generated `README.md` manually.
- Letting Contracts depend upward on Runtime, Studio, Infra, Deploy, Templates, or provider adapters.

## Current architectural direction

Keep the package boundary explicit:

```text
@ankhorage/contracts
  WHAT the portable authored/domain state is
  WHAT valid serialized structure looks like

@ankhorage/runtime
  HOW app runtime executes bindings/actions/data

@ankhorage/data-sources
  HOW API/database data operations are resolved/executed

@ankhorage/infra
  HOW runtime/backend infrastructure is generated and reconciled

@ankhorage/deploy
  HOW app distribution is inspected/planned/executed

@ankhorage/studio
  HOW canonical state is authored and presented

@ankhorage/templates
  WHICH canonical starter manifests are authored
```

The long-term direction is one shared contract graph consumed by many independent packages, not parallel package-local models.
